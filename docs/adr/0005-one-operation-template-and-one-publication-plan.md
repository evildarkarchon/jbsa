# One operation template in OperationSession, one publication plan

Packing and extracting are both mutating archive operations, and the specification gives them one contract: Primary Failure and Secondary Failure selection (JBSA-OPS-006), the Progress Snapshot phase sequence (JBSA-OPS-007), Cooperative Cancellation up to the Publication Commit, and the reported Artifact State of every affected artifact. Before this decision, each operation enforced part of that contract itself, around a `PublicationTransaction` with nine static entry points and four hidden mode flags (`extraction`, `existingTree`, `parallel`, `processingEntered`). The copies had drifted. A sparse extraction located failures by a mix of selection positions and archive entry ordinals, an unexpected `RuntimeException` ended three different ways, pack re-admitted its own failures into a second retention built with the standard Diagnostic Policy, and a late extract source-close failure finished the outcome twice. The drift was fixed first, test-first, by #83 (extraction ordinals) and #84 (unexpected throwables in pack); the restructuring below preserves behaviour.

The operation template, `OperationSession.run`, owns these mechanisms for both operations:

1. **Unexpected throwables.** A `RuntimeException` or `AssertionError` from the operation body becomes an INTERNAL `operation.internal-failure` at the phase it interrupted. A `VirtualMachineError`, or any other `Error`, still propagates after the registered resources close.
2. **Pre-publication settlement.** A body that fails before publication returns enters CLEANUP and reports zero cleaned artifacts, so every operation that entered a phase ends with CLEANUP progress.
3. **Caller-owned resources.** The body registers each resource it acquires (the pack resource budget, the stabilization spool, the extraction budget, the open source archive). The template closes them newest first, after the body and before finishing, on success and on failure, keeping ADR-0003's D10 ordering. A close failure is a CLEANUP Secondary Failure of the same outcome.
4. **One finish.** The template finishes the operation exactly once, attaching pack's Archive Parts itself. There is no self-redelivery guard and no second failure retention: a failure the session raised to its coordinator is recognised by session state (`unwound`) and is never admitted twice, so the request's Diagnostic Policy governs every failure, including whether `operation.records-truncated` is rejected.

Publication stops finishing the session. It stages, commits, cleans its own staging and returns its artifacts, while failures accumulate in the session. It exposes exactly three operations: `publish(session, budget, plan)`; `preflightArchiveTargets`, which checks a known archive-part target set before any source is read, because that check precedes any plan (ADR-0003 step 3); and the `splitPath` rule. `publish` owns these mechanisms:

1. **A sealed plan.** `Plan.ArchiveSet` holds the destination, the part writers, the Target Policy, and whether the operation already entered PROCESSING to stabilize its payloads. `Plan.Extraction` holds the root, the entries, the Target Policy, the worker snapshot and an on-staged hook. The plan's type selects the protocol: an archive set stages every part before one atomic set commit; an extraction publishes one new root or ordered per-file commits into an existing tree.
2. **Strategy inside publication.** Publication decides new root or existing tree from target preflight, and caller-thread or worker staging from the entry count and worker limit. No mode flag is reachable from a caller.
3. **One source-close action.** Each plan carries one. Publication runs it exactly once, after every admitted stage settles and before the final Publication Commit, in every strategy, including an empty plan. It replaces four mechanisms: the last sequential writer closing the archive, the last stabilized writer closing the spool, the parallel final-stage action, and the empty-selection close. If a failure ends publication first, the action does not run and the caller's registered resource closes the source. Writers only write bytes.
4. **One extraction entry shape.** `Entry(name, writer, stagedExtent, archiveOrdinal)` always carries the entry's decoded size and archive entry ordinal; there is no short form and no sentinel. The plan rejects ordinals that do not strictly increase, because Logical Plan Order depends on archive order.
5. **One on-staged hook.** Publication calls it with the archive entry ordinal, on the caller thread and in Logical Plan Order, in both extraction strategies. The extractor advances the Validation Extent there and nowhere else.
6. **The fault seam.** The package-private `FileActions` adapter is the only filesystem fault seam, and it reaches the same `publish` entry production uses, so rollback, move and cleanup faults run against production-shaped plans: a stabilized archive set, the shared planner budget, and parallel extraction. Every path-identity read publication makes, including its target containment's and the one on a parallel worker thread, goes through the same adapter, so `destination.changed-during-rollback`, a changed backup and target-state settlement are provoked without racing the real filesystem. Target containment also takes its destination pin through the adapter, so a pin or pin-release failure is injectable on the same plans. Target containment takes the adapter itself; there is no second snapshot-reader or pin-cleanup seam.
7. **Neutral target containment.** `TargetPaths` checks archive-part targets and extraction targets alike, so it is named for neither operation. Its rechecks take publication's current location instead of keeping the PREFLIGHT location, and publication no longer rebuilds a recheck failure's location by hand.

## What stays with each operation, and why

- **Entering PROCESSING for stabilization.** A stabilized pack still completes PREFLIGHT and enters PROCESSING itself, before it reads the first source. Stabilization is processing work (Q10) and runs before any part plan, or plan, can exist, so the plan's `processingEntered` flag cannot perform that step. The flag replaces publication's mutable `processingEntered` field and the separate `stabilizedArchives` entry: publication continues in PROCESSING instead of entering it again. This departs from #81's wording that the flag also replaces the pipeline's own phase calls.
- **Entry counting** stays a runtime rule on the single `StagedFile` type. Archive-set writers report each final logical entry through `completedEntry`; extraction writers must not, because publication counts each staged entry once with its staged extent. Each plan case documents its rule. Splitting the type would make the rule compile-time, but that is out of scope.
- **Source failure mapping.** The extractor merges its sequential and parallel copy loops into one. Its only strategy-dependent step is the checkpoint, which the staged file supplies: the coordinator's cancellation checkpoint on the caller thread, or the worker stop state on a private worker. Every unstructured failure to open, read or close an entry's content is SOURCE `operation.source-io` at the entry's archive ordinal, in both strategies; the extractor's source-close action reports an archive close failure as SOURCE `operation.source-io` at CLEANUP with no ordinal. Both are the mappings parallel extraction already used.
- **The budget's location.** Publication borrows the caller's budget instead of owning one for extraction. The extractor locates that budget at the normalized root and the first selected entry's archive ordinal, the plan-level evidence location JBSA-OPS-006 defines, so a PREFLIGHT budget failure is reported where it was before. Pack keeps its own budget location.
- **PREFLIGHT progress shape.** Pack advances ENTRIES per source; extract advances by the whole selection once publication has checked the output count. Snapshot timing is not a semantic guarantee, and changing it would break behaviour preservation.

## How each operation uses the template and the plan

Pack registers its budget, and the stabilization spool once opened, then publishes an archive-set plan. A streamed set holds no source of its own, so its source-close action is `SourceClose.NONE`; a stabilized set declares `processingEntered` and closes its spool as its source. Extract registers the opened archive and then its budget, builds one entry per selected archive entry around the shared copy loop, and publishes an extraction plan whose hook advances the Validation Extent and whose source-close action closes the archive. The template's registered close of the same archive or spool is a no-op once the plan's action has run.

## Consequences

A lifecycle fix is made once, in the template or in publication, rather than once per operation or per strategy. A reader can tell which protocol a publication runs from its plan's type. The restructuring changed no existing public-seam assertion. Observable differences are confined to failures no public-seam test can provoke: a raw source read or close failure in sequential extraction is now SOURCE rather than DESTINATION; an empty selection's source-close failure is located at CLEANUP rather than PREFLIGHT; the stabilization spool now closes after the last part's readback rather than before it, holding one 64 KiB window and one handle through it; and an entry joins the Validation Extent once its whole stage, including the staged identity inspection, has settled. A new mutating operation must run through the template and publish through a plan case, extending the sealed plan if its protocol differs. Locating containment rechecks at the caller (#87) moves two failures that no public-seam test can provoke to where publication observes them: a new root that changes just before its move is reported at PUBLISHING and the last entry's ordinal, the location of the move itself, and a created directory that is not the one publication made is reported at PROCESSING and its entry's ordinal. Both were previously reported at PREFLIGHT and the first entry's ordinal.

This extends [ADR-0003](0003-pure-family-adapters-behind-the-pack-pipeline.md) rather than superseding it: the family adapter contract is unchanged, and ADR-0003's setup, teardown and epilogue steps now run through the template.
