# Pure Archive Family adapters behind the Pack Pipeline

JBSA packs every Archive Family through one Pack Pipeline module (`internal/pack`). Each family contributes a stateless, pure adapter that holds only wire knowledge. The pipeline owns all I/O, lifecycle, Content Sharing, and failure handling. Before this decision, `Tes3Packer`, `BsaPacker`, and `Ba2Packer` each re-implemented the whole operation lifecycle, and those copies had already drifted apart. The drift is recorded as approved behavior changes D1–D10, Q10, and Q14 in #68.

The pipeline owns these steps, in this order:

1. Operation session, `IoContext`, and `ResourceBudget` setup and teardown. Teardown runs through the operation template in `OperationSession` (see [ADR-0005](0005-one-operation-template-and-one-publication-plan.md)).
2. Admission and planning:
   1. `adapter.admit`;
   2. source planning under the adapter's name charset;
   3. `admitted.plan`;
   4. `pack.unmatched-entry-compression`;
   5. `<prefix>.empty-entry-set`;
   6. the decoded-size limit, charged once in Logical Plan Order. A family whose Emission declares a `Chunker` (DX10 BA2) charges each entry during stabilization instead, still in Logical Plan Order, because only its envelope knows the decoded size.
3. The split loop and target preflight. Preflight always runs, for the part count the plan knows.
4. The parallel ordered-transform stage, the Content Sharing index, and the private codec map.
5. Payload placement, then the adapter's positional table patches.
6. The `OperationReport` and its Archive Parts, then the single `FailureRetention` epilogue. Publication takes one archive-set plan, and the operation template owns the epilogue (see [ADR-0005](0005-one-operation-template-and-one-publication-plan.md)).

`FamilyAdapter.admit` returns an immutable `Admitted<K>` holding all request-derived state. It exposes data (name charset, diagnostic prefix, default split target, the family's Emission, a `SplitCost` holding only its fixed and per-name terms, and the Payload Codecs the request requires) and pure functions (`plan`, `checkStored`, `layout`, `tables`, `readback`). The Emission is one sealed declaration with three cases: `Streamed` (TES3), `PerPartRecords` (versioned BSA), and `SetOwners` (BA2). The case fixes the Content Sharing scope, the comparison basis, and the payload term of the split cost together, so an impossible combination of them cannot be declared. `SetOwners` carries an optional `Chunker`, which only DX10 BA2 declares: the envelope head byte count, the per-entry working reserve, and the pure `chunk` function. Adapters perform no I/O, own no resources, and never observe cancellation. Each method is therefore testable as input → output. Family dispatch in `BethesdaArchives.pack` is an exhaustive `switch` over `ArchiveFamily`. In the same way, `PackPipeline` keeps admission and planning, then dispatches with an exhaustive `switch` over the Emission to one package-private module per strategy: `StreamedEmitter`, or `StabilizedEmitter` with a `PerPartRecordStabilizer` or a `SetOwnerStabilizer`. A dispatch method on the declaration was rejected, because it would make the adapters' types reference pipeline-private modules.

## What stays per family, and why

These choices determine output bytes pinned by Binary Conformance fixtures, so they stay with each family's adapter:

- **Sort order.** Entry order fixes table order and payload positions. TES3 orders by name hash (low word, high word, then name bytes); versioned BSA by folder then file hash.
- **Sharing key and scope.** They decide which payloads are stored once, and each family's Emission case declares them. TES3 shares per Archive Part on raw bytes. Versioned BSA compares the complete stored record, including embedded-name framing and the stored/compressed discriminator. BA2 decides owners once for the whole archive set.
- **Split cost.** It decides part membership. The families charge different fixed allowances and name costs, and BA2 charges a shared payload only for its first owner within a part. The payload term follows from the Emission case.
- **Framing.** Embedded names and decoded-size prefixes are part of the stored bytes.
- **DDS chunking and normalization, diagnostic IDs, and admission order.** These are family semantics that the Conformance Contract pins.

The pipeline only interprets these declarations. For example, `SplitCost(fixed, nameCost)` and the Emission case together state the formula `fixed + nameCost(key) + payload`, and the pipeline's `SplitPlanner` runs the one split loop. Part-owner tracking for sharing-aware costs stays inside the pipeline.

## How each family uses the pipeline

TES3 was the first family on the pipeline: it streams its parts, stores payloads only, and shares raw bytes per part. Versioned BSA followed (#71): it stabilizes every payload, compresses with zlib or the BSA LZ4 frame, and shares complete stored records per part. BA2 completed the migration (#72): it stabilizes General and DX10 payloads, compresses with zlib or raw LZ4, shares raw bytes across the whole archive set, and reads every staged part back. All three family packers are now adapters.

- **Stabilized emission.** Versioned BSA and BA2 stabilize every payload before splitting, because their split cost depends on encoded size. Stabilization is processing work, so progress enters PROCESSING before the first source is read, and publication continues in that phase. Both stabilized cases share one outline (`StabilizedEmitter`), which owns the order and the stable spool's lifetime: target preflight, enter PROCESSING, open the spool, stabilize, seal, split, layouts and writers, then publish inside the replay-window reservation. The spool closes after every part has staged and before the Publication Commit. Each case supplies only its own stabilization and replay:
  - `PerPartRecords` (versioned BSA). Each framed record is written to one ordered spool and measured; each part then shares byte-identical records while it replays them.
  - `SetOwners` (BA2). Each entry's raw bytes are written to the spool first and resolved to the earliest byte-identical raw owner in the whole set. Only a new owner is encoded. Each entry records its owners as `Segment`s; each part emits an owner once, at its first reference. The split cost charges an owner only at its first reference within a part.

  `Streamed` (TES3) never stabilizes. It carries stored, unframed payloads only, so raw-byte sharing compares exactly the stored records. The pipeline rejects any other streamed plan as an INTERNAL JBSA bug before splitting. A streamed family that compresses or frames its payloads would need its own Content Sharing rule designed first.
- **Target preflight.** It always runs before any source is read. A stabilized plan whose stored sizes are all predictable checks its exact part set; otherwise it checks only the parts it is certain to publish, which is at least the first.
- **Codecs.** Adapters name a `PayloadCodec` per entry. The pipeline's private codec map is the only place that invokes encoders. Stored, zlib, the BSA LZ4 frame, and raw LZ4 route through it. The map keeps the pipeline's policy: which encoders a transform-stage worker may run, the headroom rule (see the transform stage below), and raw LZ4 staying on the coordinator. Each Payload Codec's own facts live in the payload codec module (`internal/codec`), behind the `AdmittedCodec` that admitting it yields: its worst-case bound, its heap/native costs, its runtime capability admission, and its Codec Profile identity. The module therefore holds the one conservative zlib bound every family uses. An adapter declares the codecs a request can select in `requiredCodecs`, and the pipeline admits each one once, immediately after `admit`, before source planning. The adapter therefore never loads a native provider and stays pure, and testable, on every platform. No encoder reserves budget for itself: the pipeline reserves an admitted codec's cost, and the encoder borrows that lease. Raw LZ4 stays on the coordinator, because each call holds its whole block and multi-MiB buffers. The codec map reserves that cost per call, just before the encoder runs and outside the coordinator's all-or-nothing reservation, so an oversized block still fails at its own entry.
- **Sharing.** The `ContentSharing` index is independent of scope and basis. As the Emission case dictates, the pipeline creates one per part or one per set, and digests either the raw bytes or the framed stored record. A stored-record key also carries a stored/compressed discriminator, so a stored record never aliases a compressed one with identical bytes.
- **Header-last layout.** BA2's header points at a name table that follows the payloads. That is still only positional `tables` patches: records, the name table at the payload end, then the header. No family branches on header-first or header-last.
- **DDS and readback.** DX10 BA2's `SetOwners` Emission adds a `Chunker` whose pure `chunk` function returns DDS slices, a `Rewrite` (BGR24 to BGRA32), the canonical decoded size, and header metadata, all from the envelope head. The pipeline performs the rewrite and each slice's sharing and encoding. A `readback` declaration (validation credits, a nonconforming diagnostic ID, the Payload Codecs the readback decodes, and the stored and decoded sizes of the largest whole block each part decodes) makes the pipeline reopen and fully decode every staged part before publication. The pipeline costs the declared codecs from the ones it admitted, for those actual block sizes, so readback charges the same rule, under the same provider, as the read, and the adapter declares only family knowledge (#102).
- **The transform stage.** `TransformStage` is the only parallel stabilization path; it replaced both `ParallelSources` and `BsaTransformedSources`. It maps every worker failure the same way for all families. A skipped outcome is INTERNAL, an unstructured I/O failure is SOURCE `operation.source-io`, and any other non-fatal throwable is INTERNAL. It admits workers under one headroom rule: the sum of the codec bounds must fit a sixth of the scratch ceiling.

## Consequences

Adding or fixing lifecycle behavior happens once, not three times. Admission order and the decoded-size limit are uniform across families. TES3 table writes now happen after payload placement rather than before; that is allowed because Progress Snapshot timing is not a semantic guarantee. A family whose wire rules really need a new lifecycle step must extend the pipeline and its `Admitted` contract, rather than branch around them. Likewise, a family whose payloads fit none of the three Emission cases needs a new case, and the exhaustive `switch`es over the Emission then make the pipeline handle it.
