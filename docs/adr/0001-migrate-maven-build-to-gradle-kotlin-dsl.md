# Migrate the Maven build to Gradle with Kotlin DSL

JBSA will replace its Maven reactor with a Gradle build expressed in Kotlin DSL. The migration will preserve existing module boundaries and all consumer-visible outputs, including coordinates, artifact names and contents, JPMS module names, dependency metadata, documentation artifacts, signatures, checksums, and CLI entry points. Production code will remain Java during this migration; any Java-to-Kotlin source conversion is a separate decision.

Maven and Gradle may coexist only while build parity is being validated. Once the Gradle build satisfies the existing architecture, conformance, publication, and release gates, the repository will switch atomically to Gradle rather than maintain two authoritative builds. Shared Gradle policy may be extracted into convention plugins, but module redesign is outside this migration.

The replacement will be one Gradle multi-project build with the same six application and build-only projects. Substantial shared policy will live in Kotlin convention plugins in an included `build-logic` build. A version catalog, dependency locking, and strict checksum verification will complement—not replace—the existing compliance inventory.

Gradle will preserve the unit, integration, tagged qualification, publication-metadata, staging, and compliance lifecycles. Cross-build acceptance requires semantic artifact parity with Maven, while two clean Gradle builds must be byte-for-byte reproducible with each other. Gradle may generate local Maven publication artifacts but will not enable remote publication. Implementing the specified future `jlink`/`jpackage` distribution is outside this migration.

Ordinary compilation, formatting, unit tests, and integration tests will be portable across Windows and Linux. Oracle execution, Windows-specific filesystem behavior, native packaging, and Release Qualification remain Windows-only. Maven-specific policy assertions will remain during parallel validation and be replaced at cutover by equally strong Gradle-native assertions.

The normative specification will require a pinned Gradle build rather than abstracting the build tool away. The Gradle root will retain the `jbsa-parent` identity, and the migration will preserve the existing `target/` output layout and fixed `2026-09-03T00:00:00Z` archive timestamp. Generated output must never use the repository's tracked root `build/` automation directory. A deterministic build-layout manifest will provide a future path away from hard-coded output locations.

The default version will come from `gradle.properties`, with an explicitly validated `-Pversion=<candidate>` override applied to every project. The wrapper will pin the binary-only Gradle 9.7.1 distribution and verify both the distribution and wrapper-JAR SHA-256 checksums.

Compliance will consume a deterministic Gradle-produced resolved-production-dependency manifest together with the generated consumer POM, dependency lockfiles, strict dependency-verification metadata, and the existing licensing inventory. The aggregate SBOM will retain `jbsa-parent` as its root component and preserve its production-only component set.

Configuration cache, parallel execution, and remote caching will not be enabled during parity work. Local build caching may be enabled after parity is measured; other optimizations require separate evidence that conformance, staging, and reproducibility remain correct.

Build, dependency, SBOM, publication, staging, reproducibility, automated-conformance, and Release Qualification evidence must be regenerated for Gradle-produced release artifacts. Existing evidence remains unchanged as historical provenance and does not qualify newly produced artifacts.

Kotlin build logic will own task modeling and orchestration. Existing behavior-heavy PowerShell automation will remain where it has regression coverage, while Maven invocation and POM-source parsing will be replaced with Gradle model data and deterministic generated manifests. The build will use Gradle's core Java, application, and Maven publication capabilities together with pinned Spotless, CycloneDX, and Shadow plugins; JMH configuration will remain explicit.

The canonical complete local gate will be `gradlew clean verify`. Shared build logic will have unit and Gradle TestKit coverage, while the real multi-project build remains subject to black-box policy and conformance tests. Dependency and plugin repositories will be declared centrally, dynamic and changing dependencies will be rejected, resolution conflicts will fail, all resolvable graphs will be locked, and release builds will reject snapshot dependencies.

Implementation will proceed as reviewable commits on one migration branch. The authoritative cutover will occur in one merge only after full parity, at which point all active POMs, Maven wrapper files, and Maven-only configuration will be removed without compatibility shims. Historical Maven research and evidence will remain as provenance. Gradle and plugin upgrades will initially be manual, isolated, checksum-verified changes subject to the complete qualification gates.

The six projects will retain distinct roles: `jbsa` is the published Java library; `jbsa-cli` is the thin application; `jbsa-test-support`, `jbsa-conformance-tests`, and `jbsa-benchmarks` remain build-only; and `jbsa-dist` remains a non-Java staging and audit project. Incidental application distributions will be disabled, the benchmark standalone JAR will remain build-only, and the existing canonical staged artifact set will not expand.

To preserve consumer metadata, the unclassified LWJGL artifacts will be Gradle `api` dependencies and the Windows native classifiers will be `runtimeOnly`. Existing test sources will stay in place but unit and integration classes will run in separate tasks with deterministic class-name ordering, one fork, and the existing locale, time-zone, encoding, module-path, and native-access settings. Test reports will use Gradle-native locations beneath each project's `target/` directory.

Verification will explicitly build canonical artifacts, generate the consumer POM and compliance inputs, run pre-staging compliance, stage release inputs, and run the post-staging audit before root `verify` completes. Existing CI gate names will remain stable while invoking Gradle tasks, and a Linux portability job will supplement the authoritative Windows qualification gates.

Developer builds may run Gradle on Java 17 or newer and request an Adoptium Java 25 toolchain. The pinned Foojay resolver will provision the toolchain when no matching installation exists, while Windows and Linux/WSL qualification and reproducibility independently bind the exact reviewed Temurin `25.0.4.1+1` platform archive and checksum. Compilation will retain Java release 25, parameter metadata, UTF-8, and all lint diagnostics. Normal JPMS compilation and testing will use Gradle module-path inference, with explicit launcher arguments reserved for the existing exceptional native and classpath scenarios; black-box module tests remain authoritative.

The migration will freeze unrelated dependency, formatting, Java, and archive behavior. Maven and Gradle parity will be measured at one source revision, version, and qualification JDK across artifact payloads, JPMS and API contracts, normalized publication and SBOM metadata, runtime dependency hashes, compliance outputs, staged inputs, CLI behavior, and gate outcomes. Maven is only a temporary oracle for behavior it implements; the normative specifications and conformance tests remain authoritative.

Initial dependency-verification metadata will be reviewed against the existing dependency set, compliance inventory, and independent upstream checksums. Qualification will prove that a primed, verified cache supports an offline build without discovering dependencies. Build-layout and resolved-dependency manifests will be internal, versioned, deterministically serialized contracts rather than release assets or public API.

Active specifications, requirement bindings, developer documentation, operational procedures, and actionable local-issue instructions will move to Gradle. Imported issue bodies, comments, closed history, research, observations, and existing evidence will remain intact as provenance; potentially misleading history may receive a dated clarification instead of being rewritten.

The cutover will preserve reusable artifact inspectors and Gradle reproducibility checks, retain a final normalized parity report as historical evidence, and remove migration-only Maven comparison machinery. Generated outputs will be limited to explicitly owned directories, repository ignores and attributes will cover the Gradle wrapper and outputs, and rollback will mean reverting the coherent cutover rather than retaining a hidden Maven fallback.

CI may cache checksum-verified Gradle distributions and dependencies but not remote task outputs. Evidence-producing commands will use `--no-daemon`, preserve existing conformance exit semantics, and publish no build scans or telemetry. Performance will be measured on comparable cold and warm runs but will not displace correctness and maintainability as the acceptance criteria.

The cutover requires semantic parity, Windows `clean verify`, Linux portability, verified offline resolution, reproducible canonical artifacts, all policy and conformance gates, correct publication and staging metadata, and an automated scan proving that no active Maven instructions remain outside a reviewed historical allowlist.

Implementation order will follow dependency structure: capture the Maven baseline; establish the Gradle wrapper, settings, catalog, and build logic; port the six projects; port publication and compliance flows; establish Gradle-native policy and parity tests; validate both builds on the migration branch; update active specifications, documentation, and issue instructions; then regenerate evidence and remove Maven. The public CI gate names and the documented `run-ci-gate.ps1` interface will remain stable.

The final active-reference scan will include `.scratch/*/issues`. It will not rewrite imported issue bodies, comments, canonical links to historical Maven work, valid consumer-POM requirements, or uses of “Maven Central” as a repository proper name. Migration-only Maven comparison code will be removed at cutover, while reusable artifact inspectors, Gradle reproducibility tests, and the final parity report will remain.

The migration will freeze unrelated dependency, formatting, Java, and archive behavior. Maven and Gradle parity will be measured at one source revision, version, and qualification JDK across artifact payloads, JPMS and API contracts, normalized publication and SBOM metadata, runtime dependency hashes, compliance outputs, staged inputs, CLI behavior, and gate outcomes. Maven is only a temporary oracle for behavior it implements; the normative specifications and conformance tests remain authoritative.

Initial dependency-verification metadata will be reviewed against the existing dependency set, compliance inventory, and independent upstream checksums. Qualification will demonstrate that a primed, verified dependency cache supports an offline build. Build-layout and resolved-dependency manifests will be deterministic, versioned internal contracts rather than release assets or public API.

Current specifications, requirement bindings, development instructions, operational procedures, and actionable local issue text will be migrated to Gradle terminology and commands. Historical research, observations, issue history, comments, and evidence will remain unchanged as provenance. Repository hygiene will protect the tracked root `build/` directory, commit and verify the official Gradle wrapper JAR, and update ignore and line-ending policy.

The cutover will be recoverable by reverting its coherent Git change, not by retaining hidden Maven files. Comparable cold and warm build timings will be recorded without making an unsubstantiated performance claim. Local development may use the Gradle daemon, while CI and evidence-producing builds use `--no-daemon`. No build telemetry, automatic scan publication, or remote cache will be introduced.
