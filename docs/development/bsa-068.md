# Fallout 3, New Vegas, and Skyrim LE BSA

The maintainer-approved [52-case catalog](../reviews/issue42-cv1/README.md) is
activated, and all 52 cases passed fresh ordinary execution. Issue #42 is closed.

Issue #42 extends the existing versioned-BSA reader and writer to wire version
`0x68`. The public family is `FO3_FNV_SKYRIM_LE_BSA`; the CLI accepts `-fo3`,
`-fnv`, and `-tes5`. The three selectors describe the same archive encoding.

The implementation shares folder records, ordering, bounds checks, publication,
and JDK zlib with Oblivion. Version-specific selection stays internal. Stored,
zlib, and per-entry mixed compression are supported. Explicit archive flag
`0x0100` places a canonical full-name prefix before payload framing. Prefix
bytes remain separate from index name components and never manufacture a missing
index identity. Complete framed bytes participate in sharing comparisons.

Automatic flags follow the 0x68 rules: archive flags start at `0x0003`, legacy
menu/shader/font file flags are cleared, and embedded names require an explicit
override. The shared hash routine selects unsigned byte recurrence for 0x68.
Unqualified non-ASCII encoding remains outside canonical packing, and original
non-ASCII wire names and stored hashes remain authoritative on decode.

## Requirement trace

The governing registry is specification **0.14.0**. The original ticket's
readiness note referred to 0.13.0; the current requirements govern this work.

- `JBSA-BSA-001`–`003`: selector, header, folder/file records.
- `JBSA-BSA-005`–`009`: names, hashes, unsigned ordering, mixed framing, zlib.
- `JBSA-BSA-011`: explicit embedded-name framing and index independence.
- `JBSA-BSA-012`–`015`: flags, classification, validation, splitting and sharing.
- `JBSA-CLI-004`–`006`, `009`: aliases, codec selection, overrides and observations.
- `JBSA-CONF-001`, `007`–`014`: evidence authority, reviewed goldens, independent
  validation, differential checks and malformed cases.

Tests use the confirmed public library API, CLI, and independent conformance
boundaries. No new public provider or storage abstraction is introduced.

## Validation

The [full clean build](evidence/issue42-build.json) passed all seven reactor
modules: 445 reported tests, zero failures or errors, and seven optional skips.
The run enabled the pinned BSA oracle differentials and both performance
checkpoint versions. Separate proposal execution supplies the CV1 case results.

Use Java 17 or newer with the checked-in Gradle wrapper; Gradle supplies the Temurin Java 25
toolchain. Focused checks:

```powershell
.\gradlew.bat :jbsa:test --tests '*Bsa68PackTest' --tests '*Bsa68ReaderTest' --tests '*BsaPackTest' --tests '*BsaReaderTest'
.\gradlew.bat :jbsa-cli:test --tests '*MainTest'
.\gradlew.bat "-Djbsa.bsa.local=true" :jbsa-conformance-tests:bsaConformanceTest --tests '*Bsa068ConformanceIT'
python build/prepare-bsa-cv1-review.py --family bsa-068
pwsh -NoProfile -File build/run-bsa-cv1-review.ps1 -Family bsa-068 -OutputDirectory target/issue42-review-new
```

The BSA performance checkpoint measures matched 16 MiB stored and zlib workloads
for 0x67 and 0x68, including pack/extract time, output size, entry-prefix reads
and heap-pool peaks. It is development regression evidence, not formal PV1.

The [recorded checkpoint](evidence/issue42-performance/fresh-jvm-comparison.json)
includes an investigation of the larger heap-pool peaks in the initial shared
JUnit JVM. Repeating each version in its own 64 MiB JVM removed that difference:
stored peaks matched at 47,552,736 bytes; zlib peaks were 24,147,168 and
24,271,072 bytes. Median stored packing was 34.41/33.87 ms and zlib packing was
205.80/211.76 ms for 0x67/0x68. Output sizes matched exactly for each codec, and
decoded bytes passed validation. The initial heap delta reflects allocation/GC
history in that measurement, rather than evidence of a version-specific live
heap increase. Three measured rounds do not establish a confidence interval or
formal performance acceptance.

Golden proposals remain untrusted until reviewed and explicitly activated under
`JBSA-CONF-007`. Stored-byte comparison alone does not establish Binary
Conformance: repeatability and CPU qualification remain separate requirements.
Synthetic fixtures do not establish game acceptance or Release Qualification.

The independent game vectors cover each of `-fo3`, `-fnv`, and `-tes5` with
stored, zlib and mixed records, with and without embedded names. The oracle CLI
has a global compression switch; mixed records originate from JBSA's public
per-entry override and are cross-decoded by the oracle. The reverse direction
uses oracle stored/zlib archives. No compressed-byte identity is asserted.

Additional CV1 observations cover all automatic classifier rows, hash collisions
across interleaving folder groups and worker/source orders, every index-name
presence combination, exact embedded-prefix diagnostics, name overlays and
rejections, zlib stream consumption, and publication of split siblings.

The historical generic split recipe includes a near-2-GiB entry whose stored
size sets compression-toggle bit 30. It is not a legal single stored BSA record.
The 0x68 observation checks that rejection and uses separately specified legal
record sizes to exercise actual crossing of the 2-GiB advisory split target.
Large generated payloads remain local build outputs and are not committed.

Wire-name checks retain Windows-1252 and Windows-932 bytes under the requested
encoding. The standard profile always decodes with Windows-1252. Actual Japanese
decoding through the active-ANSI compatibility profile requires an ACP-932
Windows environment; this machine's checks do not establish that qualification.
