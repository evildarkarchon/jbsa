# GitHub distribution without Maven Central

Research date: 2026-09-02. This note supports [Choose the Maven module and artifact seams](https://github.com/evildarkarchon/jbsa/issues/8). Facts below come only from GitHub's official documentation; the recommendation is an inference for JBSA.

## Facts

### GitHub Packages' Maven registry

- **Public Maven packages are not anonymous downloads.** GitHub says an access token is required to publish or install public as well as private/internal packages. Its permissions guide adds that package pulls in most registries require a personal access token or `GITHUB_TOKEN` even when public; only the public Container registry is documented as allowing anonymous pulls. [Apache Maven registry authentication](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-apache-maven-registry#authenticating-to-github-packages), [package visibility and access](https://docs.github.com/en/packages/learn-github-packages/about-permissions-for-github-packages#visibility-and-access-permissions-for-packages)
- For a developer consuming through Maven, GitHub Packages supports only a **personal access token (classic)**. The token needs `read:packages`, the GitHub account needs read permission to the repository, and the credentials are configured in `~/.m2/settings.xml`. Publication outside Actions needs `write:packages` plus repository write permission. [Package scopes and permissions](https://docs.github.com/en/packages/learn-github-packages/about-permissions-for-github-packages#about-scopes-and-permissions-for-package-registries), [Maven token configuration](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-apache-maven-registry#authenticating-with-a-personal-access-token), [publishing permissions](https://docs.github.com/en/packages/learn-github-packages/publishing-a-package)
- A workflow in the package's repository can publish with its generated `GITHUB_TOKEN`; GitHub's Maven example grants `contents: read` and `packages: write`. Workflows can also pull with `GITHUB_TOKEN`; access to packages associated with another private repository may require explicit package access or a classic PAT with `read:packages`. [Publishing Java packages with Maven](https://docs.github.com/en/actions/tutorials/publish-packages/publish-java-packages-with-maven), [Maven workflow authentication](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-apache-maven-registry#authenticating-to-github-packages)
- Maven/Gradle packages are repository-scoped and inherit that repository's permissions and visibility. Maven clients use `https://maven.pkg.github.com/OWNER/REPOSITORY`; GitHub supports snapshots, requires the owner in lowercase in Maven settings, and rejects an `artifactId` containing characters other than lowercase letters, digits, or hyphens. [Repository-scoped package permissions](https://docs.github.com/en/packages/learn-github-packages/about-permissions-for-github-packages#permissions-for-repository-scoped-packages), [Maven registry configuration](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-apache-maven-registry), [Maven package naming](https://docs.github.com/en/actions/tutorials/publish-packages/publish-java-packages-with-maven#about-package-configuration)
- GitHub Packages usage is free for public packages. [GitHub Packages billing](https://docs.github.com/en/billing/concepts/product-billing/github-packages#how-use-of-github-packages-is-measured)

### GitHub Release assets

- A public repository is accessible to everyone on the internet, and anyone with repository read access can view its releases. GitHub's release-asset API explicitly permits listing and fetching public assets without authentication; it exposes a `browser_download_url` for direct downloads. Thus public release assets can be downloaded without a GitHub account or token. [Repository visibility](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories#about-repository-visibility), [about releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), [release-asset downloads](https://docs.github.com/en/rest/releases/assets#get-a-release-asset)
- GitHub describes releases as software packages with attached binary files. Its upload API accepts raw file data with a caller-supplied content type and does not prescribe package formats. Therefore JARs, POMs, sources JARs, Javadoc JARs, and ZIP distributions can all be attached as ordinary assets. This is a direct inference from the generic upload contract. [Upload a release asset](https://docs.github.com/en/rest/releases/assets#upload-a-release-asset), [linking directly to release assets](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)
- A release may contain up to 1,000 assets; every asset must be under 2 GiB; GitHub documents no limit on a release's total size or bandwidth. GitHub may rename filenames containing special characters or leading/trailing periods. Uploading a duplicate filename fails until the old asset is deleted. [Release quotas](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases#storage-and-bandwidth-quotas), [release-asset upload constraints](https://docs.github.com/en/rest/releases/assets#upload-a-release-asset)
- Release assets are addressed as files by release/tag, filename, or asset ID. GitHub documents Maven dependency resolution separately through the Packages Maven endpoint. Consequently, a collection of release assets is **not a Maven repository**: Maven will not obtain coordinate lookup, metadata/version resolution, or transitive dependencies merely from those downloads. This is an inference from the two documented interfaces. [Maven package installation](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-apache-maven-registry#installing-a-package), [release-asset downloads](https://docs.github.com/en/rest/releases/assets#get-a-release-asset)

## Recommendation for JBSA

Use **GitHub Releases as the primary public distribution channel**. Attach a versioned Windows ZIP containing the thin CLI JAR, library JAR, runtime dependencies, and launcher; optionally attach the individual main, sources, and Javadoc JARs for developers. A POM may be attached for transparency, but should not be presented as enabling normal Maven dependency resolution.

Do **not** make GitHub Packages the primary public channel: its Maven support is technically appropriate for coordinate-based consumption, but requiring every public consumer to create and configure a classic PAT is disproportionate friction for this project. GitHub Packages can remain an optional later channel if authenticated Maven/Gradle consumption becomes a concrete need. This distribution choice does not require changing the accepted `jbsa` library and `jbsa-cli` module/artifact seams.
