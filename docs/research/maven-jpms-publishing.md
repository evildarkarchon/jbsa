# Maven, JPMS, and Maven Central constraints for JBSA

Research date: 2026-09-02. This note supplies external facts for [Choose the Maven module and artifact seams](https://github.com/evildarkarchon/jbsa/issues/8). It distinguishes requirements imposed by Maven Central or Java 25 from project recommendations inferred from those requirements.

> **Scope update:** Maven Central publication and readiness were explicitly ruled out during the ticket's HITL decision process. The Central material below is retained only as rejected background; it does not constrain the JBSA specification.

## External requirements

### Maven Central

- A publisher must control a verified namespace (`groupId`) before publishing. Sonatype normally provisions `io.github.<username>` when the publisher signs in with that GitHub identity; a domain-derived namespace instead requires ownership verification. Therefore `io.github.evildarkarchon` is a plausible coordinate root, but its availability must still be checked in the publisher account before release. [Central namespace registration](https://central.sonatype.org/register/namespace/)
- Every deployment needs GAV coordinates and a POM. A release version may not end in `-SNAPSHOT`; non-default packaging must be declared. The POM must contain `name`, `description`, project `url`, license information, developer information, and SCM connection information. Correct dependency metadata is strongly recommended by Central rather than listed as a validation requirement. [Central publishing requirements](https://central.sonatype.org/publish/requirements/)
- Every artifact whose packaging is not `pom` must have a `-sources.jar` and `-javadoc.jar` alongside its main JAR. Central currently permits placeholder source/Javadoc JARs, but explicitly recommends accurate sources and comprehensive documentation. This rule applies to a CLI JAR as well as a library JAR. A `pom`-packaged parent/aggregator does not need those companion JARs. [Central publishing requirements](https://central.sonatype.org/publish/requirements/#supply-javadoc-and-sources)
- Every deployed file (POM, main JAR, sources JAR, Javadoc JAR, and any other deployed artifact) needs a detached PGP signature in a corresponding `.asc` file. MD5 and SHA-1 checksums are currently required; SHA-256 and SHA-512 are accepted but optional. Signature files do not need checksums, and checksum files do not need signatures. [Central publishing requirements](https://central.sonatype.org/publish/requirements/#sign-files-with-gpgpgp)
- The Central Publisher Portal's Maven plugin can assemble and upload a bundle and generates its checksums, but it does **not** generate all required source/Javadoc JARs, signatures, or required POM metadata. Build validation must cover those separately. [Publishing with Maven through Central Portal](https://central.sonatype.org/publish/publish-portal-maven/)
- Central releases are immutable: a published component is not modified or replaced; a correction is published as a new version. [Central immutability policy](https://central.sonatype.org/publish/requirements/immutability/)

### Java 25 and JPMS

- Compiling with `maven.compiler.release=25` makes `javac` enforce Java 25 language rules, class-file target, and Java SE API surface. Java 25 class files use major version 69, so an ordinary release-25 artifact requires a Java 25-or-newer runtime. [Maven Compiler Plugin: `--release`](https://maven.apache.org/plugins/maven-compiler-plugin/examples/set-compiler-release.html), [JVMS 25 class-file versions](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-4.html#jvms-4.1)
- A top-level `module-info.class` makes a JAR an explicit modular JAR. Its descriptor controls module dependencies, exported packages, opened packages, service use, and service provision. A package not exported by a normal module is inaccessible to code outside that module through ordinary Java access. [JLS 25, module declarations](https://docs.oracle.com/javase/specs/jls/se25/html/jls-7.html#jls-7.7), [Maven JAR Plugin, modular JARs](https://maven.apache.org/plugins/maven-jar-plugin/usage.html#modular-jar-files)
- The same explicit modular JAR remains usable on the class path; when placed there, it behaves as a non-modular JAR. JPMS support therefore does not require a second classifier or multi-release JAR for this Java-25-only project. Multi-release JARs solve the different problem of carrying implementations for multiple Java releases. [JAR File Specification](https://docs.oracle.com/en/java/javase/25/docs/specs/jar/jar.html#modular-jar-files)
- `Automatic-Module-Name` gives a non-modular JAR a stable module name only when it is placed on the module path. It does not provide an explicit dependency graph or encapsulation: automatic modules are treated as exporting and opening all packages and receive broad readability. Without the attribute, the module name is derived from the filename. [Java 25 `ModuleFinder`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/module/ModuleFinder.html#of(java.nio.file.Path...)), [Java 25 automatic-module modifier](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/module/ModuleDescriptor.Modifier.html#AUTOMATIC)
- The JLS calls automatic modules a migration convenience and warns that their names and exported packages may change when they become explicit modules; `javac` has warnings for `requires` on automatic modules and a stronger warning for `requires transitive`. [JLS 25, `requires`](https://docs.oracle.com/javase/specs/jls/se25/html/jls-7.html#jls-7.7.1), [Java 25 `javac` lint keys](https://docs.oracle.com/en/java/javase/25/docs/specs/man/javac.html#extra-options)
- `requires transitive` makes every module that reads the current module also read the named dependency. It is therefore part of the module's primary API. `requires static` makes a dependency mandatory at compile time but optional at run time. [JLS 25, `requires`](https://docs.oracle.com/javase/specs/jls/se25/html/jls-7.html#jls-7.7.1)
- If a native provider uses JNI, FFM restricted methods, or `System.loadLibrary`, Java 25 regards native access as illegal unless enabled for its module. Java 25 currently warns by default, while `deny` is documented as the future default. A named module can be enabled narrowly with `--enable-native-access=<module>`; class-path code can only be enabled collectively as `ALL-UNNAMED`. [Java 25 restricted methods](https://docs.oracle.com/en/java/javase/25/core/restricted-methods.html), [Java 25 restricted-method list](https://docs.oracle.com/en/java/javase/25/docs/api/restricted-list.html)

### Maven reactor, dependencies, and executable JARs

- Maven aggregation and inheritance are separate concepts. A `pom`-packaged root can aggregate child projects through `<modules>`, while children may independently inherit build configuration from a parent POM. The reactor collects projects and topologically sorts instantiated project dependencies and plugin relationships before building them. `dependencyManagement` alone does not establish reactor order. [Maven POM introduction](https://maven.apache.org/guides/introduction/introduction-to-the-pom.html#project-aggregation), [Maven multi-module guide](https://maven.apache.org/guides/mini/guide-multiple-modules.html)
- A child POM's parent is looked up from its relative path, then local repository, then remote repository. Consequently, if a published consumer POM retains a parent reference, that parent POM must also be resolvable to consumers (or the release process must publish a self-contained consumer POM). [Maven POM reference](https://maven.apache.org/pom.html#the-solution-2)
- Maven `compile` dependencies propagate to downstream projects; `runtime` dependencies appear at runtime and in tests but not at compile time; `provided` and `test` dependencies are not transitive. An `optional` dependency is omitted from downstream resolution unless the consumer redeclares it. Maven recommends declaring every dependency used directly. [Maven dependency mechanism](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html)
- Maven describes a separate module as preferable to an optional dependency when an optional feature can be split out. It also recommends a separate project for reusable test support because an attached `tests` JAR loses transitive test-scoped dependencies. [Maven optional dependencies](https://maven.apache.org/guides/introduction/introduction-to-optional-and-excludes-dependencies.html), [Maven JAR Plugin: reusable test classes](https://maven.apache.org/plugins/maven-jar-plugin/examples/create-test-jar.html)
- A thin executable JAR names its entry point with `Main-Class`; its dependencies are not embedded. `java -jar` ignores other user class-path settings, but the JAR manifest may contain relative `Class-Path` entries. A modular launch instead uses `java --module-path ... --module module/mainclass`. A modular JAR launched from the class path behaves non-modularly. [Java 25 launcher](https://docs.oracle.com/en/java/javase/25/docs/specs/man/java.html), [JAR `Class-Path` specification](https://docs.oracle.com/en/java/javase/25/docs/specs/jar/jar.html#class-path-attribute), [Maven Archiver manifest options](https://maven.apache.org/shared/maven-archiver/#manifest)
- The Maven Assembly Plugin can create a separate application bundle/distribution and select which project artifacts and dependencies it contains. This need not turn the normal CLI artifact into an uber-JAR. [Maven Assembly Plugin](https://maven.apache.org/plugins/maven-assembly-plugin/plugin-info.html), [Assembly dependency sets](https://maven.apache.org/plugins/maven-assembly-plugin/examples/single/including-and-excluding-artifacts.html)

## Evidence-backed recommendations for this ticket

These are design recommendations, not external requirements.

1. Use one deep public library artifact and one thin CLI artifact. A reasonable coordinate/module/package family is:

   | Role | Maven artifact | JPMS module | Package ownership |
   | --- | --- | --- | --- |
   | Archive library | `io.github.evildarkarchon:jbsa` | `io.github.evildarkarchon.jbsa` | Public API under `io.github.evildarkarchon.jbsa`; implementation under non-exported subpackages such as `.internal` |
   | BSArch-compatible CLI | `io.github.evildarkarchon:jbsa-cli` | `io.github.evildarkarchon.jbsa.cli` | Argument parsing, presentation, process exit, and launch code only; depends on the library's exported API |

   Do not create one Maven/JPMS module per Archive Family or codec unless a later decision identifies an independently consumable provider boundary. Those splits would weaken the intended deep library interface and multiply Central release artifacts.

2. Put `module-info.java` in both production JARs. Export only intentionally public library packages; export no library implementation packages. The CLI normally needs no exported package. Prefer dependencies with explicit stable module descriptors; tolerate an automatic dependency only as an audited migration exception. `Automatic-Module-Name` is a fallback for a non-modular release, not a substitute for an explicit descriptor here.

3. Keep third-party types out of the library's public method signatures where practical. A mandatory implementation dependency should remain accurately declared in the POM so Maven consumers receive it, but use ordinary JPMS `requires` so callers do not read it through the library. Use `requires transitive` only when an external module's types are deliberately part of the exported API. Keep Maven optionality and JPMS runtime optionality aligned; do not mark a dependency optional merely to make the POM look small.

4. Use a `pom`-packaged reactor root for shared versions/plugin policy and aggregation. Publish that parent POM if the released library and CLI POMs retain it. The initial reactor need not exceed `jbsa` and `jbsa-cli`; keep conformance/integration tests as unpublished reactor modules, and add an unpublished `jbsa-test-support` module only when two test modules genuinely share fixture builders or validators. Avoid an attached `tests` classifier for shared support.

5. Keep `jbsa-cli.jar` thin. For the JPMS-native Windows distribution, assemble a ZIP containing the CLI JAR, library JAR, runtime dependencies under `lib/`, and a `.cmd` launcher that invokes `java --module-path ... --module io.github.evildarkarchon.jbsa.cli/<main-class>`. This preserves module boundaries and permits narrow `--enable-native-access=<provider-module>` if a native codec is eventually selected. A `Main-Class`/manifest `Class-Path` launch can be offered for class-path compatibility, but `java -jar` does not exercise JPMS encapsulation.

6. Configure the release build to attach real source and Javadoc JARs for both published JAR artifacts, sign all deployed files, and validate the complete Central bundle. Keep Portal credentials and signing material out of the POM and repository. Actual publication and release automation remain outside the Wayfinder destination.

## Decision checks still owned by the ticket

- Confirm the available Central namespace before freezing `groupId`; repository ownership alone does not prove that the Publisher Portal account has the namespace.
- Decide whether the CLI JAR itself is a Central artifact or only part of a later binary distribution. If it is published to Central, it incurs the same sources/Javadoc/signing obligations as the library.
- Decide whether a native provider is selected. If so, give it a separate replaceable module and make the distribution launcher own the Java 25 native-access flag.
- Decide whether shared test-support code actually exists. Do not create a public or published test-support artifact speculatively.
