# Java 25 and Windows facts for archive I/O and resource lifetimes

Research date: 2026-09-02. This note supplies external facts for [Choose the archive I/O and resource-lifetime model](https://github.com/evildarkarchon/jbsa/issues/12). It uses only the Java 25 API specification, the OpenJDK 25 GA reference-implementation source, and Microsoft Windows documentation. It deliberately records constraints without choosing JBSA's product or architecture policy.

## Large files, offsets, and channel behavior

- `SeekableByteChannel` and `FileChannel` represent position, size, truncation size, and positional I/O offsets as `long`. Setting a position beyond the current end is legal; a later read reports end-of-file, while a later write grows the file. `FileChannel.read(dst, position)` and `write(src, position)` do not change the channel's current position. The Java API therefore has no signed-32-bit addressing limit at 2 GiB, although each individual `ByteBuffer` transfer remains bounded as described below. [Java 25 `SeekableByteChannel`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/SeekableByteChannel.html), [Java 25 `FileChannel`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html)
- A `FileChannel` is safe for use by multiple concurrent threads, but only one operation involving its mutable current position or file size can be in progress at once. Explicit-position operations may proceed concurrently, but whether they actually do so is implementation-dependent. [Java 25 `FileChannel` concurrency contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html)
- `FileChannel.read` can return zero or `-1`, and `write` can return zero. `transferTo` and `transferFrom` take `long` positions/counts but may transfer fewer bytes than requested and return a `long` actual count, possibly zero. The contract does not make one invocation an all-bytes operation. [Java 25 `FileChannel` reads and writes](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html#read(java.nio.ByteBuffer)), [Java 25 `FileChannel.transferTo`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html#transferTo(long,long,java.nio.channels.WritableByteChannel))

## Heap, direct, and mapped memory

- `ByteBuffer` allocation and indexing are `int`-sized: `allocate`, `allocateDirect`, capacity, position, and limit all use `int`. `ByteBuffer.allocate(int)` returns a non-direct buffer backed by an accessible `byte[]`; direct buffers allow the JVM to make a best effort to avoid intermediate native-I/O copies. Direct buffers have higher allocation/deallocation costs, may occupy memory outside the garbage-collected heap, and Oracle recommends using them only where measurement shows a benefit. Both allocation factories produce buffers in big-endian byte order unless changed explicitly. [Java 25 `ByteBuffer`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/ByteBuffer.html), [Java 25 `Buffer`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/Buffer.html)
- The classic `FileChannel.map(mode, position, size)` returns a `MappedByteBuffer` and rejects a mapping size greater than `Integer.MAX_VALUE`. Its mapping remains valid until the buffer is garbage-collected, is independent of the originating channel, and is not invalidated by closing that channel. Neither `ByteBuffer` nor `MappedByteBuffer` implements `AutoCloseable` or exposes a public unmap method. [Java 25 `FileChannel.map` returning `MappedByteBuffer`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html#map(java.nio.channels.FileChannel.MapMode,long,long)), [Java 25 `MappedByteBuffer`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/MappedByteBuffer.html)
- Java 25 also exposes `FileChannel.map(mode, offset, size, arena)`, returning a mapped `MemorySegment`. Its offset and size are `long`; the API rejects negative values or `long` overflow rather than imposing `Integer.MAX_VALUE`. A closeable arena controls the mapping lifetime and unmaps the segment when closed. The reference implementation supplies this method, while the abstract method's default implementation is permitted to throw `UnsupportedOperationException` for a non-JDK/custom `FileChannel` implementation. [Java 25 arena-based `FileChannel.map`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html#map(java.nio.channels.FileChannel.MapMode,long,long,java.lang.foreign.Arena)), [OpenJDK 25 `FileChannelImpl`](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/java.base/share/classes/sun/nio/ch/FileChannelImpl.java#L1344-L1364)
- A `MemorySegment` reports its byte size and accepts slice offsets/sizes as `long`. Converting it to a `ByteBuffer` fails if the segment exceeds `Integer.MAX_VALUE`; a smaller `ByteBuffer` view is tied to the segment's scope and becomes inaccessible after the arena closes. Consequently, a segment can address a mapping larger than one buffer while any `ByteBuffer`-only consumer still operates on bounded slices/windows. [Java 25 `MemorySegment.byteSize` and `asSlice`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/foreign/MemorySegment.html), [Java 25 `MemorySegment.asByteBuffer`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/foreign/MemorySegment.html#asByteBuffer())
- `Arena.ofConfined()` segments are accessible only by the arena's owner thread; `Arena.ofShared()` segments are accessible by any thread. Closing a closeable arena invalidates all associated segments and releases their backing off-heap regions. Close is not idempotent and can fail if a segment is being accessed concurrently. `Arena.ofAuto()` is GC-managed and cannot be closed explicitly. [Java 25 `Arena`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/foreign/Arena.html)
- `MemorySegment.unload()` and `MappedByteBuffer.load()`/`isLoaded()` concern best-effort physical-memory residency; they do not end the mapping lifetime. Arena close is the public Java 25 lifetime operation that unmaps an arena-backed mapped segment. [Java 25 `MemorySegment` mapped operations](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/foreign/MemorySegment.html#unload()), [Java 25 `MappedByteBuffer`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/MappedByteBuffer.html)
- `FileChannel.force(metaData)` guarantees that changes made through that channel are written to a local storage device; passing `true` also requests metadata. It may not force changes made through a mapped buffer or segment, which has its own `force()` operation. No such device guarantee is made for non-local storage. [Java 25 `FileChannel.force`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html#force(boolean)), [Java 25 `MemorySegment.force`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/foreign/MemorySegment.html#force())

## Streaming, interruption, and close ownership

- `FileChannel` implements `InterruptibleChannel`. Interrupting a thread blocked in channel I/O closes the channel, sets the thread's interrupt status, and throws `ClosedByInterruptException`; entering a blocking operation with interrupt status already set has the same close-and-throw effect. Closing an interruptible channel from another thread causes blocked operations to receive `AsynchronousCloseException`. This is a whole-channel effect, not cancellation confined to one read or entry view. [Java 25 `InterruptibleChannel`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/InterruptibleChannel.html), [Java 25 `ClosedByInterruptException`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/ClosedByInterruptException.html)
- `Channels.newInputStream(channel)` and `newOutputStream(channel)` are unbuffered adapters, and closing the returned stream closes the wrapped channel. The reverse adapters, `Channels.newChannel(stream)`, likewise close the wrapped stream when the channel closes. Using the standard adapter over a shared archive-owned channel therefore changes the wrapped resource's lifetime unless another adapter or independently owned channel mediates closure. [Java 25 `Channels`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/Channels.html)
- A `FileChannel` obtained from `FileInputStream`, `FileOutputStream`, or `RandomAccessFile` shares both position and underlying state with the originating object, and closing the channel closes that originating object. [Java 25 `FileChannel` stream relationship](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html)
- Virtual threads are intended for tasks that spend most of their time blocked, commonly on I/O, and are not intended for long-running CPU-intensive operations. In Java 25, blocking I/O can release the carrier thread, while blocking during native or foreign-function execution can pin it and reduce scalability. These contracts separate the scheduling characteristics of blocking file I/O from CPU-bound compression and native codec work; they do not themselves impose a concurrency limit. [Java 25 `Thread` virtual-thread contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.html), [Java 25 Virtual Threads guide](https://docs.oracle.com/en/java/javase/25/core/java-core-libraries-developer-guide.pdf#page=8)

## Temporary storage and cleanup

- `Files.createTempFile(dir, ...)` creates a new empty file that did not previously exist in a caller-selected directory. Its overload without `dir` uses the default temporary-file directory. The API explicitly describes temp creation as only part of a facility and points to `DELETE_ON_CLOSE`, a shutdown hook, or `File.deleteOnExit()` for cleanup. [Java 25 `Files.createTempFile`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/Files.html#createTempFile(java.nio.file.Path,java.lang.String,java.lang.String,java.nio.file.attribute.FileAttribute...))
- `StandardOpenOption.DELETE_ON_CLOSE` makes a best-effort deletion attempt on close and, if close is omitted, another best-effort attempt at JVM termination. Its timing and mechanics are implementation-specific, it is intended for a work file used by one JVM, and the API cautions against concurrent external use and security-sensitive replacement races. [Java 25 `StandardOpenOption.DELETE_ON_CLOSE`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/StandardOpenOption.html#DELETE_ON_CLOSE)
- `Files.delete`/`deleteIfExists` may fail on operating systems that do not permit removing an open file. `File.deleteOnExit()` only attempts deletion on normal JVM termination, cannot be canceled after registration, and does not provide abnormal-termination cleanup. [Java 25 `Files.delete`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/Files.html#delete(java.nio.file.Path)), [Java 25 `File.deleteOnExit`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/io/File.html#deleteOnExit())
- `Cleaner` invokes fallback actions only after the registered object becomes phantom reachable; its processing thread is a daemon, and actions should be fast and non-blocking. Explicit `AutoCloseable.close()` can invoke the same action earlier, but GC-triggered timing is not an explicit-lifetime contract. [Java 25 `Cleaner`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ref/Cleaner.html)

## Atomic moves and output durability

### Portable Java API contract

- With `Files.move(source, target, ATOMIC_MOVE)`, the move is an atomic filesystem operation and all other copy options are ignored. If the target already exists, replacement versus failure is implementation-specific. If the provider cannot perform an atomic move, including cases such as crossing `FileStore` or provider boundaries, it throws `AtomicMoveNotSupportedException`. Without `ATOMIC_MOVE`, existence checking and moving need not be atomic, and a failed non-atomic move can leave source/target state undefined. [Java 25 `Files.move`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...))
- `ATOMIC_MOVE` specifies atomic filesystem visibility, not a storage-flush operation. The Java durability APIs are separately `FileChannel.force`, mapped-buffer/segment `force`, or the `SYNC`/`DSYNC` open options, which require synchronous content-and-metadata or content-only updates respectively. [Java 25 `Files.move`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...)), [Java 25 synchronized open options](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/StandardOpenOption.html#SYNC)

### Current OpenJDK 25 Windows provider

- The OpenJDK 25 GA Windows provider currently implements the atomic branch with `MoveFileEx(source, target, MOVEFILE_REPLACE_EXISTING)` and translates `ERROR_NOT_SAME_DEVICE` to `AtomicMoveNotSupportedException`. Thus this specific implementation replaces an existing target even though portable Java leaves that result implementation-specific. It does not pass `MOVEFILE_WRITE_THROUGH` in the atomic branch. This is an implementation fact, not a portable API promise. [OpenJDK 25 `WindowsFileCopy.move`](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/java.base/windows/classes/sun/nio/fs/WindowsFileCopy.java#L257-L295)
- Microsoft specifies that `MOVEFILE_REPLACE_EXISTING` replaces an existing destination file when permissions allow, while the separate `MOVEFILE_WRITE_THROUGH` flag delays return until a copy/delete-style move is flushed. The OpenJDK flag choice above therefore does not add the optional Windows write-through request to Java's atomic-move operation. [Microsoft `MoveFileExW`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)

## Windows handle and mapping lifetimes

- In the OpenJDK 25 GA Windows provider, ordinary file-channel opens enable `FILE_SHARE_READ`, `FILE_SHARE_WRITE`, and `FILE_SHARE_DELETE` by default. `DELETE_ON_CLOSE` becomes Windows `FILE_FLAG_DELETE_ON_CLOSE`, and Java `SYNC`/`DSYNC` become `FILE_FLAG_WRITE_THROUGH`. These are reference-implementation details, not requirements on every Java file-system provider. [OpenJDK 25 `WindowsChannelFactory`](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/java.base/windows/classes/sun/nio/fs/WindowsChannelFactory.java#L60-L76), [OpenJDK 25 Windows open flags](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/java.base/windows/classes/sun/nio/fs/WindowsChannelFactory.java#L220-L254)
- Windows sharing modes remain in effect until a handle closes. Deleting or renaming through another open is permitted only when existing handles' sharing modes permit delete access; `FILE_FLAG_DELETE_ON_CLOSE` defers deletion until all relevant handles are closed. [Microsoft `CreateFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew), [Microsoft `DeleteFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-deletefilew)
- On Windows, closing the original file handle does not end a mapped view: the system holds the corresponding file open until the last view is unmapped. Modified mapped pages are written lazily unless explicitly flushed. Combined with Java's lifetime rules, a classic `MappedByteBuffer` can keep the Windows mapping alive after its `FileChannel` closes, while closing the arena of an arena-backed mapped segment deterministically requests unmapping. [Microsoft `UnmapViewOfFile`](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-unmapviewoffile), [Java 25 arena-based `FileChannel.map`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html#map(java.nio.channels.FileChannel.MapMode,long,long,java.lang.foreign.Arena))

## File locks, sharing denial, and open-file identity

- A Java `FileLock` covers a byte range and is held on behalf of the whole JVM, so it is not a mutex between threads in that JVM. For other programs, a shared lock excludes overlapping exclusive locks but permits overlapping shared locks, while an exclusive lock excludes either type; locks held on the same file by one JVM may not overlap at all. A platform that lacks shared locks may promote a shared request to exclusive. Actual prevention of file-content access is system-dependent, so Java recommends treating locks as advisory. Closing a channel can release locks held through other channels to the same file on some systems, and locking can conflict with memory mapping. [Java 25 `FileLock`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileLock.html)
- OpenJDK 25 on Windows implements Java file locks with `LockFileEx`, setting `LOCKFILE_EXCLUSIVE_LOCK` for a non-shared request. Windows denies other processes both ordinary reads and writes in an exclusively locked range; a shared lock denies ordinary writes but permits reads. Windows explicitly states that byte-range locks do **not** prevent reads or writes through mapped file views. [OpenJDK 25 Windows lock implementation](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/java.base/windows/native/libnio/ch/FileDispatcherImpl.c#L464-L508), [Microsoft `LockFileEx`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)
- A byte-range `FileLock` does not itself govern rename or deletion. On Windows those operations require delete access, and whether another handle may request delete, read, or write access is controlled separately by the `FILE_SHARE_DELETE`, `FILE_SHARE_READ`, and `FILE_SHARE_WRITE` modes established when each handle is opened. [Microsoft `CreateFileW` access and sharing modes](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
- Java 25's `com.sun.nio.file.ExtendedOpenOption` declares `NOSHARE_READ`, `NOSHARE_WRITE`, and `NOSHARE_DELETE`, but it is a JDK-specific API in the `jdk.unsupported` module rather than a Java SE API. The module exports `com.sun.nio.file` without qualification, so a named client module can use it with `requires jdk.unsupported` and does not need `--add-exports`; the class contract says the options are supported only on some platforms by the Sun provider implementation. JEP 260 classifies this retained API family as unsupported and warns that compatibility can be lost in a future release. [OpenJDK 25 `ExtendedOpenOption`](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/jdk.unsupported/share/classes/com/sun/nio/file/ExtendedOpenOption.java#L28-L50), [OpenJDK 25 `jdk.unsupported` descriptor](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/jdk.unsupported/share/classes/module-info.java#L26-L30), [Java 25 API overview](https://docs.oracle.com/en/java/javase/25/docs/api/index.html), [JEP 260 retained critical internal APIs](https://openjdk.org/jeps/260#critical-internal-apis-not-encapsulated-in-jdk-9)
- The OpenJDK 25 Windows provider enables all three Windows share modes by default. Each `NOSHARE_*` option clears its corresponding share bit before `CreateFile` is called. Windows rejects an open whose requested access conflicts with existing handles' share modes, and keeps every handle's sharing choices in effect until that handle closes; delete access includes rename. Thus `NOSHARE_DELETE` and `NOSHARE_WRITE` are open-time Windows sharing constraints, distinct from byte-range locking, and the opening operation itself can fail if a conflicting handle already exists. [OpenJDK 25 `WindowsChannelFactory`](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/java.base/windows/classes/sun/nio/fs/WindowsChannelFactory.java#L79-L123), [OpenJDK 25 Windows share flags](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/java.base/windows/classes/sun/nio/fs/WindowsChannelFactory.java#L229-L243), [Microsoft `CreateFileW`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew)
- Windows associates a successfully opened handle with a file object until the handle closes, while the file data referenced by handles is shared and requires synchronization. Windows also documents that an existing handle can continue to access a file's data after its visible name is removed under POSIX deletion semantics. Taken together with the OpenJDK provider's handle-backed `FileChannel`, this implies that a successful rename or path replacement does not retarget an already-open channel: it continues to address the object it opened, while a later open of the path can address the replacement. This is a Windows/OpenJDK inference, not a portable Java guarantee. [Microsoft file handles](https://learn.microsoft.com/en-us/windows/win32/fileio/file-handles), [Microsoft extended file disposition](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddk/ns-ntddk-_file_disposition_information_ex), [OpenJDK 25 `WindowsChannelFactory`](https://github.com/openjdk/jdk/blob/jdk-25%2B36/src/java.base/windows/classes/sun/nio/fs/WindowsChannelFactory.java#L130-L158)
- Keeping one channel open stabilizes that file-object identity but does not create a content snapshot. Compatible handles can still modify or truncate the same object; Java does not specify cross-process view consistency, and mapped content can change at any time or become inaccessible after truncation. A byte-range lock can block ordinary Windows I/O in its range, but mapped access remains a documented bypass. [Java 25 `FileChannel` consistency contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html), [Java 25 `MappedByteBuffer`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/MappedByteBuffer.html), [Microsoft `LockFileEx`](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)

## Decision constraints exposed by these facts

These are consequences of the cited contracts, not decisions for JBSA:

- Large-archive addressing can remain `long` end to end, but `ByteBuffer`-oriented parsing and codec calls still cross bounded windows no larger than `Integer.MAX_VALUE`.
- Classic mapped buffers do not provide deterministic public unmapping; arena-backed mapped segments do, with an explicit thread-access and close contract.
- Interruption-based cancellation and ordinary adapter closure are unsafe to treat as view-local when several lazy entry readers share one `FileChannel`.
- Atomic replacement, data flushing, rename durability, and abandoned-temporary cleanup are distinct guarantees and failure surfaces.
- Virtual threads can scale blocking Java I/O but do not make CPU-bound or native codec execution faster or inherently bounded.
- Byte-range locking and Windows open-time sharing denial are different mechanisms: neither portable `FileLock` nor a default OpenJDK Windows channel alone guarantees both immutable content and a stable pathname.
- An open Windows channel can retain the identity of the object it opened across a permitted rename or replacement, while in-place writes still change that same object's content.
