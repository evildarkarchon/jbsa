# Conformance oracle and fixture strategy

Status: decision research for the pinned Reference Snapshot  
Reference Snapshot: [`TES5Edit/TES5Edit@fd1e36020b2b5b6217e553dc0038983146a2e2dd`](https://github.com/TES5Edit/TES5Edit/tree/fd1e36020b2b5b6217e553dc0038983146a2e2dd) (`xedit-4.1.5q`)  
Target environment: Windows 11 x64, NTFS, Java 25

## Decision

Use a layered oracle, not a single round trip:

1. **Pinned BSArch behavior oracle.** A locally provisioned `BSArch.exe` whose SHA-256 is pinned in an oracle manifest defines the Reference Snapshot's observable CLI behavior. Prefer the maintainer-produced `xEdit 4.1.5q` binary after manual acquisition from the first-party xEdit Discord; retain a separately built executable as a provenance cross-check, not as proof that the maintainer binary was reproduced bit-for-bit.
2. **Committed redistributable goldens.** Generate small archives only from project-authored inputs, record their complete provenance, and commit the inputs, archives, extracted-byte hashes, structural expectations, and normalized CLI observations.
3. **Cross-direction differential tests.** The Java reader must decode BSArch-produced archives, and pinned BSArch must decode Java-produced archives. Compare entry names, metadata, and uncompressed bytes; require archive byte identity only for cases shown to be deterministic.
4. **Independent corroboration.** Check archive structure and payloads with a separately implemented parser/tool and, for release qualification, with the applicable Bethesda Creation Kit tool and game runtime. xEdit is not independent because its `.bsa`/`.ba2` handling was replaced with BSArch's shared code ([pinned changelog](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/whatsnew.md#L1398-L1404)).
5. **Ignored local game corpus.** Exercise legally obtained game archives only through an opt-in local Maven profile. Never commit the archives, extracted assets, or derived archives containing those assets.

Conformance is the gate. A result is not conformant merely because Java can read what Java wrote, or because BSArch can read what BSArch wrote.

## Why the binary must be provisioned and pinned

The Reference Snapshot is an exact tag and commit, and its console entry point reports `BSArch v1.0` ([source](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/Core/wbBSArchive.pas#L20-L23)). Its GitHub release has **only** autogenerated source ZIP and tarball assets—no executable ([release](https://github.com/TES5Edit/TES5Edit/releases/tag/xedit-4.1.5q), [expanded assets](https://github.com/TES5Edit/TES5Edit/releases/expanded_assets/xedit-4.1.5q)). The pinned README instead directs users to the `#xedit-builds` channel of the first-party xEdit Discord for current builds ([README](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/README.md#L11-L15)). Therefore an exact maintainer binary is feasible to obtain, but it is not reproducibly downloadable from a stable public release URL and GitHub publishes no digest for it.

Provision it outside Git as, for example:

```text
tests/tools/local/bsarch/xedit-4.1.5q/BSArch.exe
tests/tools/local/bsarch/xedit-4.1.5q/oracle-local.json
```

Both paths must be ignored. Commit a non-secret manifest template and allow a committed manifest to contain only reproducibility metadata—not the executable—after distribution rights are reviewed. The manifest should contain:

- source tag and full commit;
- original release archive name and SHA-256, if available;
- `BSArch.exe` SHA-256 and PE file/product versions;
- Authenticode status and signer, even when unsigned;
- acquisition channel and date;
- Windows build, architecture, filesystem, active ANSI/OEM code pages, and CPU model;
- a smoke-test capture of no-argument help, including raw stdout, raw stderr, and exit code.

The harness must reject a binary whose digest does not match the selected oracle manifest. Merely finding `BSArch.exe` on `PATH` is insufficient.

## Source-build feasibility and limitations

The project is a Delphi console application. Its project file defaults to `Release` and `Win64`, emits `Build\BSArch.exe`, and directly references the archive, command-line, compression, DDS, hashing, and stream units ([project settings](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/BSArch.dproj#L1-L12), [outputs and search paths](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/BSArch.dproj#L55-L72), [units](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/BSArch.dproj#L94-L103)). The pinned README recommends Delphi 12 Community Edition and requires recursive submodule initialization ([build prerequisites](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/README.md#L59-L78)). Git documents that submodule update checks out the exact gitlink revisions recorded by the superproject ([`git submodule update`](https://git-scm.com/docs/git-submodule#Documentation/git-submodule.txt-update--init--remote-N--no-fetch)).

For an external disposable checkout—not the repository's read-only `TES5Edit` directory—the intended command-line build is:

```powershell
git clone --recurse-submodules https://github.com/TES5Edit/TES5Edit.git reference-build
git -C reference-build checkout --detach fd1e36020b2b5b6217e553dc0038983146a2e2dd
git -C reference-build submodule update --init --recursive

# Run inside a RAD Studio environment initialized for Delphi 12.
MSBuild.exe reference-build\BSArch.dproj /t:Build /p:Config=Release /p:Platform=Win64
```

Embarcadero documents both `.dproj` builds through `MSBuild.exe` and the initialized RAD Studio Command Prompt environment ([MSBuild](https://docwiki.embarcadero.com/RADStudio/en/MSBuild), [build command syntax](https://docwiki.embarcadero.com/RADStudio/Sydney/en/Building_a_Project_Using_an_MSBuild_Command)). The two project-specific compression dependencies are pinned gitlinks: `libdeflate-pas@c044fe1…` and `lz4-delphi@6d6244e…` ([`.gitmodules`](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/.gitmodules), [tree](https://github.com/TES5Edit/TES5Edit/tree/fd1e36020b2b5b6217e553dc0038983146a2e2dd/External)). The libdeflate binding statically links Win32/Win64 object files unless explicitly configured for a DLL ([binding source](https://github.com/ElminsterAU/libdeflate-pas/blob/c044fe1a7b0e2e9930c6a5110c7bd194a4872c91/libdeflate.pas#L3276-L3338)); the pinned LZ4 binding ships object files and is tested with Delphi 12 ([binding tree and README](https://github.com/ElminsterAU/lz4-delphi/tree/6d6244eb768797c1a5aa6346848e6ee68d096e0f)). The BSArch CLI does not invoke BSArchPro's optional `xtexconv.exe` path, so the ordinary CLI oracle has no adjacent codec-tool requirement.

Local feasibility check on 2026-09-02 found Delphi Studio `23.0` and `DCC64.EXE`, but `dcc64 -h` returned `This version of the product does not support command line compiling.` The installed license can therefore support a manual IDE build but cannot automate the documented command-line build on this workstation. A CI/repeatable source build needs a Delphi license/environment that enables the command-line compiler.

A source build is still not a bit-reproducible reconstruction of the maintainer executable: the release does not publish its precise Delphi patch level, compiler configuration, binary digest, or build attestation. Record the source-built executable's own hash and use it to confirm behavior. Do not substitute it silently for the maintainer binary.

## Deterministic invocation contract

Invoke the executable directly from Java, with one argument-list element per BSArch argument. Do not pass through `cmd.exe` or PowerShell. Java 25's `ProcessBuilder` exposes an explicit command list, working directory, environment, and separate stdout/stderr pipes ([Java 25 `ProcessBuilder`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/ProcessBuilder.html)); `Process` exposes bounded waits and exit status ([Java 25 `Process`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Process.html)).

For every oracle run:

- use a fresh, short, ASCII-only directory on NTFS;
- use the absolute, digest-checked oracle executable path;
- set an explicit working directory and isolated `TEMP`/`TMP` beneath the run directory;
- provide no stdin and close the child stdin immediately;
- consume stdout and stderr concurrently as **raw bytes** to avoid pipe deadlock and preserve carriage-return progress updates;
- enforce a command-specific timeout; on timeout capture diagnostics, terminate the process tree, and fail the test;
- record the exact argument array, selected environment, start/end timestamps, raw streams, exit code, and SHA-256 of every input and output;
- never infer success solely from exit code: inspect expected artifacts and the normalized diagnostic model too.

Use explicit pack settings rather than defaults:

```text
BSArch.exe pack <ordered-file-1+ordered-file-2+...> <archive> <format> -split:0 -share:no -mt:no
BSArch.exe pack <ordered-files> <archive> <format> -z:<codec> -split:0 -share:no -mt:no
BSArch.exe unpack <archive> <existing-output-directory> -mt:no
BSArch.exe <archive> -list
BSArch.exe <archive> -dump
```

The `<format>` value is one of `-tes3`, `-tes4`, `-fo3`/`-fnv`/`-tes5`, `-sse`, `-fo4`, `-fo4dds`, `-sf1`, or `-sf1dds` ([CLI source](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/BSArch.dpr#L145-L189), [help](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/BSArch.dpr#L382-L430)). Supported codec choices are format-specific: TES3 none; TES4/FO3 zlib; SSE LZ4 frame; FO4 zlib; Starfield general zlib or LZ4; Starfield DDS LZ4 or zlib ([reference table](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/Core/wbBSArchive.pas#L160-L187)).

### Why ordered individual files are required

For BSA families, the writer sorts entries by format hashes; for TES3 single-thread mode it also sorts the source list alphabetically ([sorting](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/Core/wbBSArchive.pas#L1512-L1544), [TES3 packing](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/Core/wbBSArchive.pas#L2350-L2399)). BA2 construction, however, retains the input-list order, while adding a source directory uses `TDirectory.GetFiles(...)` without a subsequent sort ([BA2 creation](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/Core/wbBSArchive.pas#L1732-L1781), [directory enumeration](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/Core/wbBSArchive.pas#L2829-L2846)). Golden generation must therefore enumerate fixture files in ordinal archive-name order itself and pass those files as ordered `+`-joined sources. Directory-source behavior remains a semantic fixture, not a byte-golden fixture.

Generate each candidate golden at least five times in fresh directories. Commit an archive SHA-256 only if all runs agree. Repeat the experiment on the supported baseline CPU and at least one different x64 CPU before declaring compressed bytes portable across processors. If bytes vary, compare structure and extracted payloads instead.

### Output normalization

Always retain raw capture for audit, but compare a normalized event model in routine tests:

- preserve the banner and stable messages;
- convert carriage-return progress rewrites into a final progress event;
- replace the `Done in <duration>.` value with a duration placeholder;
- replace run-root absolute paths with logical fixture paths;
- retain warnings, exception class/message, and exit code verbatim for ASCII fixtures.

Use ASCII names for the normative CLI-output corpus. Archive strings are not reliably Unicode: an independent Bethesda archive implementation documents them as binary/system-code-page strings rather than guaranteed Unicode ([`ba2` string model](https://ryan-rsm-mckenzie.github.io/bsa-rs/ba2/index.html#%C2%A7a-note-on-strings)). Put non-ASCII names and host paths in a separate Windows code-page matrix; record raw bytes plus active ANSI/OEM code pages, and do not decode with Java's default charset.

## Exit-code contract, including the known gap

The pinned program sets exit code `1` for top-level exceptions and pack/unpack processing failures ([pack failure](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/BSArch.dpr#L241-L252), [unpack failure](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/BSArch.dpr#L342-L350), [top-level handler](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/BSArch.dpr#L619-L633)). Archive-info errors are different: `DoInfo` catches the exception and prints `Error: ...` without setting a non-zero code ([source](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/BSArch.dpr#L95-L126)).

Record that as an explicit compatibility quirk:

- reference capture for an existing malformed archive: expected diagnostic plus observed exit `0`;
- Java library: typed failure;
- example Java CLI: non-zero failure exit, unless a later compatibility decision explicitly demands the apparent BSArch defect.

This honors the agreed policy: valid encoding/decoding is normative, while apparent defects are preserved only through an explicit compatibility decision backed by differential evidence.

## Committed fixture corpus

Store generated fixtures under a format-oriented layout such as:

```text
tests/fixtures/generated/
  sources/<corpus-id>/...
  archives/<format>/<case-id>.(bsa|ba2)
  manifests/<case-id>.json
  observations/<case-id>/info.normalized.txt
  observations/<case-id>/list.normalized.txt
  observations/<case-id>/dump.normalized.txt
```

Every committed fixture must be built exclusively from project-authored bytes and carry a project license/provenance note. Never derive committed fixtures from Bethesda game archives or third-party mods. The manifest must include:

- fixture schema version and case ID;
- generator revision and deterministic seed, if generated by code;
- ordered archive names plus source SHA-256 and size;
- archive family, version, flags, codec, compression setting, sharing setting, and split setting;
- exact BSArch argument array and oracle manifest ID;
- archive SHA-256 and size;
- expected entry order, names, metadata, compressed/uncompressed sizes, and payload SHA-256;
- raw-capture hashes, normalized observations, and exit code;
- validators used, their pinned versions/digests, and results;
- whether byte identity or semantic equivalence is the asserted contract.

### Minimal source corpus

Use small, intentionally shaped project-owned inputs:

- empty, one-byte, and ordinary UTF-8 text payloads;
- repeated bytes and deterministically seeded incompressible bytes on both sides of the reference's 8 MiB libdeflate threshold ([compression source](https://github.com/TES5Edit/TES5Edit/blob/fd1e36020b2b5b6217e553dc0038983146a2e2dd/Core/wbCompression.pas#L20-L50)); keep the larger threshold case generated in tests if repository size is a concern;
- identical payloads under different names for `-share:yes` and `-share:no`;
- nested folders, case variants, extension variants, and hash-order edge cases;
- multiple ordered sources with a later source overriding an earlier same-name entry;
- valid, tiny DDS files covering legacy and DX10 headers, mip counts, block-compressed formats, cubemaps, and chunk boundaries for FO4/Starfield texture BA2. Generate them from code against Microsoft's DDS structures, or with a digest-pinned DirectXTex `texconv`; Microsoft publishes both a full DDS reader/writer and the packed DDS header definitions ([DirectXTex](https://github.com/microsoft/DirectXTex), [`DDS.h`](https://github.com/microsoft/DirectXTex/blob/main/DirectXTex/DDS.h)).

Create cases for every supported archive family and valid codec combination. Add dedicated cases for detected/default flags, explicit `-af`/`-ff`, filters, sharing, source merging/override, list/dump, invalid arguments, truncated/corrupt input, and duplicate/hash-collision behavior. Large split-boundary, maximum-count, and performance corpora belong under ignored local fixtures because `-split:N` is expressed in GiB and meaningful boundaries are too large for ordinary Git.

## Differential assertions

For each format case:

1. **BSArch pack -> Java read:** assert detected family/version, ordered logical names, flags and exposed metadata, uncompressed size, and SHA-256 of every entry.
2. **BSArch pack -> Java extract:** assert the complete output tree against the source-tree manifest.
3. **Java pack -> BSArch info/list/dump:** require parse success and compare normalized structure/metadata.
4. **Java pack -> BSArch unpack:** compare the complete output tree byte-for-byte with the input manifest.
5. **Independent parser/tool:** require open/list/full extraction where that validator supports the family; compare payload hashes and metadata it exposes.
6. **Byte identity:** require whole-archive SHA-256 equality only for case IDs whose manifest says `comparison: byte-exact` after repeated determinism proof. Otherwise require semantic equivalence and separately report archive size.

Do not use repacking alone to validate a reader, because a matching writer defect can hide a matching reader defect.

## Independent validators

No single secondary validator should become a second normative oracle. Pin validators by commit/version and use disagreements as investigation triggers:

- **Bethesda tools and game runtime:** the relevant Creation Kit's archive tool and the target game loader are the strongest independent acceptance checks for outputs intended for that game. Bethesda makes the Fallout 4 and Skyrim Special Edition Creation Kits available on Steam ([Bethesda support](https://help.bethesda.net/app/answers/detail/a_id/55366/~/will-the-creation-kit-for-fallout-4-and-skyrim-be-available-on-steam%253F)). These checks are local/manual unless automation is separately proven, and must be pinned to the tested game/Creation Kit version.
- **Ryan McKenzie's `bsa`/`ba2`:** this is a separate C++/Rust implementation covering TES3, TES4-family, and FO4-family models; its public documentation demonstrates independent reading/writing and DDS support ([C++ project](https://github.com/Ryan-rsm-McKenzie/bsa), [examples](https://ryan-rsm-mckenzie.github.io/bsa/), [Rust format modules](https://ryan-rsm-mckenzie.github.io/bsa-rs/ba2/index.html)). It is a library, so a tiny digest-pinned validator executable must be maintained or built for CI.
- **Mod Organizer 2 BSATK/BSA extractor or BSA Browser CLI:** useful Windows extraction corroboration with released binaries, but coverage and known bugs must be pinned per version. Mod Organizer 2 explicitly uses BSATK for BSA/BA2 preview and describes format/version limitations in release notes ([MO2 release notes](https://github.com/Modorganizer2/modorganizer/releases)); BSA Browser documents browse/extract support for the Elder Scrolls and Fallout archive families ([project](https://github.com/AlexxEG/BSA_Browser)). Treat these as advisory, especially for newest Starfield/FO4-NG variants.
- **DirectXTex:** validate every reconstructed DDS independently. Its API reads legacy and DX10-extension DDS and reports metadata ([DDS I/O](https://github.com/microsoft/DirectXTex/wiki/DirectXTex#dds-io-functions)).

xEdit itself can be a regression consumer but cannot satisfy the independent-validator layer because it shares the Reference Snapshot's archive implementation.

## Safe local game-archive profile

The repository already ignores `tests/fixtures/local`. Keep proprietary/local material there or point to it with an environment variable such as `JBSA_LOCAL_FIXTURES`. Use an opt-in Maven profile, for example `-Plocal-fixtures`, that is skipped by default when the directory is absent.

Rules for the profile:

- discover archives only from an explicit allowlisted root; never scan all game libraries or user directories;
- open source archives read-only and write extraction/output only to a fresh temporary directory;
- store the local manifest, filenames, paths, archive hashes, and extracted bytes under the ignored root;
- never create a new archive containing extracted Bethesda or mod assets;
- do not stage or upload local failure artifacts; CI artifacts must be limited to metadata and logs that contain no asset bytes;
- record game edition/version and archive SHA-256 so automatic game updates cannot silently change a baseline;
- report skipped local tests distinctly from passing tests.

This is a conservative operational boundary, not a legal opinion. Bethesda's Creation Kit EULA licenses the editor rather than selling it and restricts unauthorized copying/distribution of the editor and owned content ([official EULA](https://store.steampowered.com/eula/1946180_eula_0)). Project-authored fixture bytes avoid that dependency entirely.

## Automation tiers

| Tier | Runs by default | Material | Purpose |
|---|---:|---|---|
| Unit | Yes | generated in-memory bytes | hashes, headers, codecs, malformed structures |
| Committed golden | Yes | project-authored inputs and small BSArch goldens | stable conformance on every build |
| Oracle differential | Opt-in / controlled Windows CI | local digest-pinned `BSArch.exe` | Java/Reference cross-direction behavior |
| Independent validator | Controlled Windows CI | pinned third-party validator(s) | reduce shared-implementation blind spots |
| Local game corpus | Developer opt-in | ignored legal game installations | breadth, real-world compatibility, performance |
| Game/Creation Kit acceptance | Release qualification | installed official tools/games | end-to-end loadability |

The default build must never download Discord binaries, Creation Kits, games, or proprietary fixtures.

## Unavoidable gaps

1. **No stable public `4.1.5q` executable or published digest.** Manual acquisition and local hashing are required.
2. **No attested maintainer build recipe.** A source build can match behavior but cannot establish executable bit identity.
3. **Current workstation cannot automate Delphi compilation.** The installed Delphi 12 license rejects command-line compiling; a manual IDE build or different licensed build environment is required.
4. **No public Bethesda archive specification covering the entire matrix.** Source implementations plus official tool/game acceptance are the practical evidence hierarchy.
5. **Game-loader acceptance is not generally headless.** It remains a release-qualification step until a safe, deterministic per-game probe is demonstrated.
6. **Official game assets and tools cannot be made ordinary CI dependencies.** Licensing, account ownership, installation paths, and updates make them local-only.
7. **Console text contains nondeterminism.** Elapsed time, progress carriage returns, absolute paths, locale, and code pages prevent raw-output goldens across machines.
8. **Compressed byte identity is not assumed.** CPU dispatch, library/compiler versions, input order, sharing, and concurrency must be empirically controlled; semantic equality remains the portable contract.
9. **Independent-tool coverage is uneven.** New Starfield, FO4-NG, DDS chunking, Xbox texture, and malformed-input behavior may have only the Reference Snapshot and game runtime as available evidence.
10. **Known reference defects require policy decisions.** Archive-info errors currently print an error with exit `0`; other inconsistencies discovered by differential tests must be catalogued rather than automatically copied.

## Exit criteria for the future implementation plan

The conformance infrastructure is ready when:

- one maintainer or source-built Reference Snapshot executable is locally provisioned with a complete digest manifest;
- repeated-run experiments classify every committed fixture as byte-exact or semantic;
- every supported family has at least one read and one write golden, and every valid codec has a compressed case;
- texture BA2 has independently validated DDS fixtures;
- the Java 25 runner captures raw stdout, raw stderr, timeout, and exit code without a shell;
- at least one independent parser validates each broad family, with official game/Creation Kit checks documented for release qualification;
- local-game tests are opt-in, read-only, reproducibly inventoried, and demonstrably excluded from Git and CI artifacts;
- the archive-info exit-code quirk and every other discovered reference discrepancy are represented as named compatibility decisions.
